# Procedural whole-object room rules

`Web/wwwroot/data/procedural-object-room-rules.json` is the furnishing configuration used by the whole-object map foundry at `Web/wwwroot/procedural-object-maps.html`. It selects room templates from a seeded theme, then places approved whole-object sprites within the existing generated room geometry. The foundry previews a 20×16 map with three generated rooms. This is visual authoring; **Play** hands the existing game a canonical map and collision tiles, not these newly reconstructed sprite images.

## Theme and furnishing rules

The foundry exposes three stable theme IDs: `guild`, `safe-rest`, and `machinery`. A theme’s `roomTypes` entries assign positive integer weights to room templates. A template contains furnishing selectors. Each selector groups interchangeable manifest `objectIds`, sets the integer grid footprint and allowed quarter-turn rotations, and gives a requested count range. `priority` determines placement order; higher-priority large fixtures reserve space before decoration. A selector’s `min` is a requested target, not a guarantee: if geometry, clearance, or connectivity leave no valid cell, the generator records a diagnostic rather than breaking the map.

`placement` guides where an object can go: `wall` requires the full footprint to touch a compatible room boundary, `center` prefers locations nearest the room center, and `anywhere` accepts any safe floor footprint. Quarter turns are applied before the renderer uniformly fits the image inside its grid footprint; the sprite is never stretched. `blocksMovement` controls every cell in the object footprint. Low-priority rugs and grates can be nonblocking. `clearance` reserves extra cells around larger furniture and service fixtures. The one-cell approaches around doors, start, and exit are protected independently of that setting.

Templates can also contain `assemblies`. An assembly is placed atomically: member sprites use integer `offset` and `footprint` rectangles relative to a derived group envelope, fixed local rotations, and one shared quarter-turn transform. The assembly’s `min`/`max` count follows the same requested-target rules as a furnishing selector: if an atomic bundle cannot fit, generation records a diagnostic instead of placing a partial cluster. Its `access` rectangles remain walkable and reserved; group `clearance` applies outside the envelope. A member `supportEdge` such as `north` requires that full edge to meet the generated boundary after group rotation. Members on the `underlay` layer may overlap props and access cells without blocking them; props cannot overlap each other. This creates small, readable furnishings rather than independent random placements.

The 11 current assemblies cover entry check-in, guild and commons table seating, guild cots, rest beds and lounge benches, workshop gear/lever stations, rail/junction runs, and crate/barrel stockpiles in guild, rest, and maintenance storage. Within these assemblies, table chairs use fixed inward-facing rotations; the assembled bed/cot has its head edge against the wall and reserved side or foot access. Optional standalone furnishings outside assemblies retain their own wall-placement semantics. Matching standalone selectors are removed so the same furniture is not scattered again around its cluster.

Room floor affinity is represented by theme `floorTag: "stone"`; selectors declare `surfaceAffinity: ["floor:stone"]`. The core retries its existing room partitioner up to 48 times on the 20×16 map, preferring rooms at least 5×5 cells; the accepted geometry seed and attempt count are recorded. On smaller boards, any leftover room-like partition narrower or shorter than four cells becomes an unfurnished passage with a diagnostic. The core creates reciprocal north/east/south/west (`N/E/S/W`) edge tags from generated floor and wall geometry, checks neighboring edges for agreement, and only attaches wall-placed furnishings to a compatible full boundary. These connector tags describe map geometry; they are not claims that the object sprites include directional wall connectors. Route and reserved-point reachability are checked after blocking placements.

## Asset coverage

The rules select from 32 of the 46 approved whole-object manifest records. Selector alternatives share a role where their shapes are suitable for the same footprint: wooden and green chairs; wooden tables and benches; the two field cots; crate variants; rugs; and potted plants. The manifest remains authoritative for each sprite’s exact asset path, native dimensions, fractional reference `gridFootprint`, tags, and provenance. Rule footprints are integer map cells chosen for this generator and can use uniform contain fitting; they do not overwrite that source metadata.

The selected families cover guild entry/common/bunk/supply rooms, rest bunks and lounges, maintenance workshops/rail bays/storage, commons, sanitation, and vending supply rooms. The 14 records not selected by these room rules are intentionally outside these themes: `ab-clean-door-double-wood-brass`, `ab-clean-wall-straight-navy`, `cd-door-threshold`, and `cd-wall-straight` (room boundaries are generated by core); `ab-clean-wheelchair-blue`; the illustrative creatures `cd-llama` and `cd-swine-boss`; and `cd-dozer`, `cd-explosive-cart`, `cd-hay-trough`, `cd-red-carpet`, `cd-stair-module`, `cd-throne`, and `cd-trap-machine`. No room requires every library object, and no creature is inserted as mandatory content. The creature drawings are illustrative whole-object art, not canonical likeness claims.

## Use and verification

Serve the site over HTTP with the runtime’s referenced room-kit and whole-object asset files available, then open `/procedural-object-maps.html`. The controls select a theme and seed; the map can be generated again, inspected with grid/collision/route overlays, and exported as JSON. The JSON records the seed, selected templates, placements, blockers, generated edge tags, connectivity route, and diagnostics.

The core suite verifies 78 maps across all three themes (72 theme/seed cases, four boundary-size cases, and two underlay regressions), 843 object placements in 220 atomic assemblies, and 17 distinct layouts. It checks deterministic repeats, reachability, placement and access constraints, export collision, invalid-input rejection, and source immutability. Browser smoke checks cover theme selection, controls, export, disclosure text, and mobile layout. A valid small room can contain no furnishings when every candidate conflicts with protected routes or clearances. Edge validation checks logical reciprocal adjacency; it does not certify seamless rendered wall artwork or canonical room layouts.

## Standalone download

`standalone.html` embeds the actual generator modules, rules, and canonical manifest; sprite images load from an immutable AI-Art revision and require internet access. Rebuild it with `python3 Tools/build_procedural_object_standalone.py`. Standalone **Play** is disabled because a downloaded page cannot hand saved-map storage to the game origin. **Export JSON** downloads a canonical playable map: import it in the game through **Save & options**. This uses existing runtime tiles and collision, rather than the preview’s whole-object sprites. The game-hosted foundry retains its same-origin Play handoff.

This is an initial procedural starter and furnishing review tool, not a reconstruction of the 36 concept scenes or a finished semantic room-design system.
