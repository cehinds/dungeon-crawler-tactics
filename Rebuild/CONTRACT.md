# Rebuild contract
All public JSON uses camelCase public fields; serializer IncludeFields=true. Namespace DccRebuild.
Bridge Initialize(string contentJson, int seed), Dispatch(string commandJson), GetSave(), LoadSave(string).
Command fields: type, direction, targetId, actorId, skillId, itemId, x, y, manaSpend. Types move/interact/select/moveUnit/forecast/confirm/endUnit/endTurn/rest/equip/useItem/retry/buy/acknowledgeReward/advanceEnemyTurn.
View: mode (explore,battle,defeat,complete), message, seed, turn, selectedId, questStage, gold, party[], inventory[], world, battle, forecast, journal[], cleared[], unlockedEvents[], destroyedPropIds[], destroyedEncounterObjectIds[], floor, availability[]. Availability rows expose `{kind,id,name,available,unlocked,reason}`.
Unit fields include id,name,x,y,hp,maxHp,mp,maxMp,level,xp,power,armor,moved,acted,ended,equipment,skills[],ranks,skillPractice,temporaryRankModifiers,statuses,tags, and skillProgress[]. Inventory entries are `{itemId,count}`.
World API: static World.Build(int seed) returns WorldMap {width,height,tiles:string[],objects:WorldObject[],spawnX,spawnY}; tiles indexed y*width+x, '#' wall '.' floor. WorldObject {id,kind,name,x,y,description}; kind guide,safe,encounter,boss,exit,chest. Engine stores cleared object IDs. Map must include guide id mordecai, safe id safe-room, encounter ids false-guild/goblin-workshop/hoarder/juicer, boss id ball-of-swine, exit id exit. Story false-guild -> guide -> goblin-workshop -> ball-of-swine -> exit; hoarder/juicer optional after guide. World rendering receives these objects with cleared bool copied in view.
Combat content, progression, and effect rules are authored in `floor-one-rpg.json`. The embedded `content-catalog.json` supplies the live typed `characters`, `locations`, `rumors`, `recipes`, `storyEvents`, `facilities`, `classes`, `temporaryModifiers`, and additional `sources`. Its `characters[]` is the live roster source because the typed registry prefers it when present; `floor-one-rpg.json.party[]` is retained compatibility metadata, not a second live roster. Edit typed character records to change active membership or starting skills. The registry keeps stable content IDs distinct from runtime IDs. Every catalog definition carries tags, a player-facing description, source references `{sourceId,locator,confidence}`, adaptation status, and availability `{minFloor,maxFloor,active,requiredEvents}`. Source references must resolve to registered sources; use locator `unknown` where retained research supplies no honest page/chapter locator.

Catalog characters use `{id,runtimeId,name,deployable,skillIds,...}`. Only Carl and Donut deploy on Floor One; Mordecai is an NPC. Catalog locations use `worldObjectId` and `visitStatus`; rumor records are separate from locations and do not imply a visit. Recipes can be retained as inactive research-only definitions. Story events bind to existing quest events through `{trigger,triggerId}`; they do not create parallel quest stages. Facilities may describe future Floor 3 class selection, which is unavailable on Floor One. Item `rankModifiers` are typed skill-ID to signed rank values and must be marked adapted or source-approved. Skills expose `permissionMaxRank` separately from `rankCapacity`; Floor One permission is rank 5, while any future higher mastery requires explicit per-skill permission. `temporaryModifiers` define adapted status-based rank modifiers; they are not applied automatically to starting units.

`effectRules` supplies bounded unit/object reactions, damage bonuses, and tag semantics. Reactions contain `{id,targetKind,trigger,priority,triggerTags,requiredTargetTags,excludedTargetTags,removeTags,operations}`. The authored Floor One rules ignite oil on fire, suppress burning with water, and chain an explosion from a destroyed object tagged `destructible` and `explosive`. Item kind is weapon/armor/charm/consumable. Skill IDs punch,powerful-strike,bomb,magic-missile,claw; elements physical,arcane,fire. Enemy fallback values supported. Party remains Carl and Donut; there are no Floor One selectable classes. Equipment IDs are chosen by kind from content.
Battle view `{width,height,phase,units[],enemies[],obstacles[],effectObjects[],hazards[],effectEvents[],effectRevision,encounterId,theme,composition,tiles[],props[]}`. `EffectObject` has `{id,assetId,propId,x,y,width,height,hp,blocksMovement,blocksSight,destroyed,tags}` and `EffectHazard` has `{id,tag,x,y,duration,strength}`. Only whitelisted world assets become persistent destructible props; encounter-owned destructible objects use `destroyedEncounterObjectIds` receipts. `targetKind` supports enemy, ally, self, object, cell, and enemyOrObject. Forecasts expose event previews and target coordinates; forecast and commit share the resolver. Most encounters use a 10 × 8 board. `goblin-workshop` and `ball-of-swine` use the generated industrial-sewer room as their battle board; both currently use an 18 × 11 footprint. `World.BuildArena(seed, encounterId)` returns this room-derived board for those two encounters, translating exploration props to room-relative coordinates and treating every non-floor tile as an obstacle. Forecast `{actorId,targetId,skillId,damage,baseDamage,cost,reaction,valid,x,y,events[],affectedCells[],friendlyFire}`. `baseDamage` is initial impact power before target defenses; `damage` reports the selected unit’s defended impact, or pre-defense impact for a cell/object. Each skill-hit unit resolves its own armor and first matching damage bonus. Environmental fixed-damage operations retain their existing behavior. `affectedCells` contains the clipped Manhattan blast footprint plus any chained explosion footprints; `friendlyFire` flags any positive party damage event, including chains. Battle includes `effectRevision`. moveUnit x/y max Manhattan 3, no crossing obstacles/units. select actorId; forecast targetId/skillId then confirm; endUnit actorId; endTurn. Each unit one move and one action in either order. Enemies then move and attack. Rest and save at safe room; GetSave only allowed adjacent to safe room. Invalid commands return view message, no state change.

Skills default to `damageBasis: "power"`. `damageBasis: "unarmed"` requires a valid physical `baseSkillId`; Powerful Strike references `punch`. Its pre-defense basis is the actor’s current Punch rank effect, `round(actor.power * Punch.powerMultiplier) + Punch.power`, then the Strike row multiplier and power are applied. Both rounds use midpoint away from zero. Strike requires the actor to know its baseline skill and have no weapon equipped. Authored Strike power is zero and rank-3/4/5 multipliers are 1.5/1.75/2; these exact factors are adaptations.

Improvised Bomb retains `targetKind: "enemyOrObject"`, `effectRadius: 1`, and adds `allowGroundTarget: true`. Forecast commands accept coordinates `x/y` with an empty `targetId`, or existing direct enemy/object IDs. A direct ID supplies its current coordinates. Blast resolution includes allies, enemies and destructible objects; existing oil and explosion reactions still apply, with no new burning rider. The initial blast uses Manhattan distance, clipped to the board. Its 2-mana cost is an adapted resource cost; no charge inventory or crafting is introduced.

World also includes rooms[], optional decorative water ~ (impassable), door and discovery object kinds (inspect descriptions). Root view x/y are exploration position; cleared[] holds completed object IDs. Bare confirm accepts pending forecast. Carl cannot equip weapon kind.

World generation records `generationVersion`. Version 1 is the archived legacy layout; versions 2 and 3 retain their historical concept grammars as migration checkpoints. Historical v1/v2/v3 maps retain their 60 × 38 dimensions. New seeded worlds use version 4 on a 90 × 52 map with 22 × 16 room sectors, which shares an 18 × 11 inset industrial-sewer workshop/boss room and arena composition, real floor crossings through side water channels, and a northern gate/corridor right of center. Save migration accepts supported v1, v2 and v3 checkpoints, verifies their persisted geometry against the corresponding historical generator, regenerates the current v4 world, and preserves validated player progress. Invalid or inconsistent checkpoints are rejected without applying partial state. These generators are compatibility/migration data, not interchangeable descriptions of current generated output.

Browser architecture overlays are presentation only. Bridge decks cover existing floor crossings between water cells; they never create walkability. Wall faces/caps derive from wall boundaries, and doorway details derive from open corridor boundaries. Props retain their explicit collision footprints. Visual overlap does not override C# tiles, obstacles or movement rules.

Version-4 room rules may specify `tileRows`: exactly `height` strings of exactly `width` characters, using `#`, `.`, and `~`. C# validates and applies this authored footprint before prop placement. The industrial profile reserves a 12 × 6 central area and uses asymmetric three-column water wings with explicit three-cell-long dry crossings. Industrial party/enemy starting cells lie on the enlarged central floor; other encounters retain their existing spawn layout.

`WorldProp.layer == "wallfixture"` identifies art mounted on blocked masonry, including industrial machinery, pipes and gate torches. Version-4 authored placement accepts these fixtures on `#`; validation requires every fixture cell to remain `#`. Solid fixtures retain collision, while nonblocking decorative fixtures may overlap the same masonry. The renderer excludes this layer from the furniture floor-restoration mask and sorts it with foreground scenery, so mounted art cannot turn wall pixels into apparent floor. The northern industrial apron is masonry around the explicit gate opening, with the authored eastern water inset retained.

Progression content in `floor-one-rpg.json` is authored under root `progression`: `levels` contains exactly 20 ordered rows `{level,totalXp,hpGain,manaGain,powerGain,armorGain}`. `totalXp` is cumulative; gains apply on entering the level and level 1 has zero gains. `practicePerUse` is successful uses earned per qualifying skill use. Each skill has `startingRank` and authored `ranks` with `{rank,practiceRequired,power,cost,range,powerMultiplier,manaOptions?,manaPowerPerPoint?}`. Practice thresholds count cumulative successful uses from the starting rank; that starting rank has threshold zero. Rank rows replace the skill's corresponding tactical values. `manaOptions` lists selectable mana spends; `manaPowerPerPoint` defines the adapted power increase per mana above the row's `cost`. Current rank-5 Magic Missile exposes 3/4/5/6 mana spends. Powerful Strike starts at rank 3. Commands accept optional `manaSpend`. Forecasts expose `{actorId,targetId,skillId,damage,baseDamage,affectedCells,friendlyFire,cost,manaSpend,trainedRank,effectiveRank,effectRank,range,reaction,valid}`. Unit views expose `skillPractice` by skill ID and `skillProgress[]` entries `{skillId,trainedRank,effectiveRank,effectRank,gearBonusRank,practice,practiceToNext,practiceProgressPercent,maxRank,cost,manaOptions,canUse,nextEffect,resource,effect,disabledReason}`, plus `{xpToNext,maxLevel,xpProgressPercent,nextLevelEffect}`. Encounter rows may define `xpReward` and `goldReward`; these are authored adaptations. Save envelopes use `{version,state}`; version 3 is current and versions 1 and 2 migrate to it. Migrations validate story gates, supported modifiers and statuses, world geometry, destructible world prop receipts, and encounter object receipts before applying state. Corrupt or unsupported state is rejected without partial application.


Content and asset validation commands are `dotnet run --project Rebuild/Tests -c Release -- --validate-content` and `python3 Tools/validate_assets.py --wwwroot Web/publish/wwwroot --self-test`. Run the complete core regression suite with `dotnet run --project Rebuild/Tests -c Release`.


## Block B loop and preparation contract

Root content `resupplyOffers[]` contains catalog definitions with `{id,name,itemId,quantity,goldCost,...provenance,availability}`. Each offer references an implemented restorative consumable. Offers are repeatable and share the existing safe-room adjacency check; there is no finite stock. The authored offers reuse `item.health_tonic` and `item.mana_draught` at 8 and 10 gold, one per purchase. `buy` uses `targetId` as the offer ID. `acknowledgeReward` clears a transient reward display without granting anything.

Encounter `itemRewards[]` rows are `{itemId,count}` and grant once with the encounter’s existing gold and per-crawler XP. View `reward` exposes `{id,sourceId,sourceKind,name,gold,items[],party[]}`; party rows contain `{actorId,xp,levelBefore,levelAfter}`. A receipt is presentation data, excluded from save state, and cannot grant rewards on acknowledgement or load. Existing cleared IDs remain the durable reward-once authority.

View `safeRoom` exposes `{safeRoomId,reason,restAllowed,saveAllowed,preparationAllowed,resupplyAllowed}`. Any adjacent runtime `safe` object qualifies in exploration; named safe places and the camp retain distinct source evidence. View `equipmentPreviews[]`, `consumablePreviews[]` and `resupplyOffers[]` come from C# validation. Equipment previews report ownership/count, equipped crawler, power/armor/rank deltas and a rejection reason. Equipment counts include equipped copies; a single copy cannot be equipped by both crawlers. Empty `itemId` on `equip` removes current gear. `ownerId` restrictions and Carl’s weapon restriction apply in the core. Restorative previews reject unavailable, exhausted or ineffective items. Purchases validate safe-room adjacency, availability, funds and inventory capacity atomically.

Services, rewards, numeric effects, prices and ownership restrictions are authored adaptations. Existing item IDs and supported save migrations remain compatible. Research-only recipes, Floor 3 classes and later house systems remain outside this loop. See `BLOCK-B-CHECKLIST.md` for completed core/browser acceptance evidence and scope limits.

Item `startingCount` defaults to zero and is validated from 0 through 999. New games receive the authored quantity without auto-equipping. Only Carl’s underpants/backpack and Donut’s tiara author `startingCount: 1`; their combat bonuses remain zero. Loading an existing save preserves its inventory without backfilling starting gear.
